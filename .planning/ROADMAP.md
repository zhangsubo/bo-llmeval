### Phase 1: 基础设施与数据模型

**目标：** 建立 PostgreSQL schema、核心领域模型和 FastAPI 骨架，为后续开发提供稳定基础。

**成功标准：**
1. 数据库迁移可执行，所有核心表创建成功
2. FastAPI 应用可启动，健康检查端点返回 200
3. SQLAlchemy 模型与数据库 schema 一致
4. 基础 CRUD API 端点可通过 Postman/curl 调用

**需求映射：**
- EXEC-01: PostgreSQL 作为唯一数据库和队列
- 数据库 schema 设计（供应商、连接、模型、数据集、Tokenizer、任务、Run、请求、Attempt）
- 核心领域模型类（SQLAlchemy ORM）
- FastAPI 应用骨架和路由结构
- Alembic 数据库迁移配置
- 开发环境 Docker Compose 配置
- 基础错误处理和日志配置
- 健康检查端点

**依赖：** 无

**风险：**
- PostgreSQL JSON 字段和分位数聚合函数需要验证
- 大规模逐请求数据的索引策略需要提前设计

---

### Phase 2: 供应商与连接管理

**目标：** 实现供应商、连接、模型部署的完整 CRUD，以及连接测试和模型同步功能。

**成功标准：**
1. 可以创建供应商和服务连接，API Key 加密存储
2. 连接测试可以验证流式和非流式 Chat Completions
3. 可以通过 `/v1/models` 自动同步模型列表
4. 可以手工录入模型 ID
5. 前端页面可以完成新供应商接入流程（10 分钟内）

**需求映射：**
- SUPP-01: 创建供应商记录
- SUPP-02: 创建服务连接
- SUPP-03: 测试连接的流式和非流式能力
- SUPP-04: 自动同步模型列表
- SUPP-05: 手工录入模型 ID
- SUPP-06: 替换 API Key
- SUPP-07: API Key 加密存储
- MODEL-01: 创建模型部署记录
- MODEL-02: 创建模型对比组
- MODEL-04: 维护模型价格

**依赖：** Phase 1

**风险：**
- 供应商 API 兼容性差异可能导致连接测试失败率高
- API Key 加密需要安全的主密钥管理方案

---

### Phase 3: 测试资源管理

**目标：** 实现 Tokenizer、数据集和测试方案模板的管理，支持下载、上传、校验和版本管理。

**成功标准：**
1. 可以从 ModelScope/Hugging Face 下载 Tokenizer
2. 可以上传本地 Tokenizer
3. 可以下载内置质量数据集
4. 可以上传自定义数据集（JSONL/CSV）
5. 数据集上传执行全文件校验
6. 系统内置测试方案模板可用
7. 可以复制并自定义模板

**需求映射：**
- RES-01: 下载并缓存 Tokenizer
- RES-02: 上传本地 Tokenizer
- RES-03: 内置 tiktoken encoding
- RES-04: 下载内置质量数据集
- RES-05: 上传自定义数据集
- RES-06: 全文件校验
- RES-07: 系统内置测试方案模板
- RES-08: 复制并自定义模板
- MODEL-03: 对比组指定默认 Tokenizer
- MODEL-05: 任务快照记录价格版本

**依赖：** Phase 1

**风险：**
- 数据集 license 审核需要明确流程
- Tokenizer 下载失败需要友好降级

---

### Phase 4: 任务引擎核心

**目标：** 实现任务创建、强制预检、PostgreSQL FIFO 队列和 Worker 执行框架。

**成功标准：**
1. 可以从模板创建评测任务草稿
2. 强制预检可以检测所有阻断条件
3. 任务可以进入 PostgreSQL FIFO 队列
4. Worker 可以从队列认领 Run 并执行
5. 支持串行和并行 Run
6. Worker 异常时 Run 标记为中断失败

**需求映射：**
- TASK-01: 从模板创建评测任务草稿
- TASK-02: 选择一个或多个模型部署
- TASK-03: 选择串行或并行运行
- TASK-04: 确认配置参数
- TASK-05: 执行强制预检
- TASK-06: 展示预检结果
- TASK-07: 冻结配置快照并进入队列
- EXEC-02: 全局并发控制

**依赖：** Phase 2, Phase 3

**风险：**
- PostgreSQL FIFO 队列的并发控制需要使用 SKIP LOCKED
- Worker lease 和 fencing token 机制需要仔细设计

---

### Phase 5: 性能评测

**目标：** 实现性能测试执行、指标采集（Latency、TTFT、TPOT、ITL、吞吐）和双口径 Token 统计。

**成功标准：**
1. 可以执行固定并发、固定 RPS、阶梯负载性能测试
2. 可以记录每个请求的完整时序和性能指标
3. 可以同时记录供应商 usage 和本地 Tokenizer Token 数据
4. 冷启动、预热和稳态独立统计
5. 性能请求不自动重试

**需求映射：**
- EXEC-03: FIFO 执行
- EXEC-04: 支持多种负载模式
- EXEC-05: 预热和冷启动
- EXEC-06: 内置长度预设
- EXEC-07: 使用 EvalScope Python API
- PERF-01: 记录性能指标
- PERF-02: 双口径 Token 统计
- PERF-03: 提供分位数统计
- PERF-04: 独立聚合冷启动和稳态

**依赖：** Phase 4

**风险：**
- EvalScope API 集成可能需要源码阅读和定制
- 流式 Token 边界识别需要使用 Tokenizer 统一编码

---

### Phase 6: 质量评测与代码沙箱

**目标：** 实现客观质量评测和代码执行隔离，支持 HumanEval、MBPP 等代码生成测试。

**成功标准：**
1. 可以执行客观质量评测（exact match、regex、多项选择等）
2. 质量请求可以有限自动重试
3. 代码测试在独立代码 Worker 的隔离容器中执行
4. 代码执行容器禁止外网、受资源限制
5. 保存编译/运行状态和测试结果

**需求映射：**
- PERF-05: 性能请求不自动重试
- QUAL-01: 客观质量评分
- QUAL-02: 质量请求有限自动重试
- QUAL-03: 代码执行隔离
- QUAL-04: 代码执行容器限制
- PROTO-02: 多轮对话

**依赖：** Phase 5

**风险：**
- 代码沙箱安全隔离需要充分测试
- 代码执行超时和资源限制需要合理配置

---

### Phase 7: 监控、取消与重试

**目标：** 实现任务实时监控、即时取消、人工重试和一键复测功能。

**成功标准：**
1. 监控页面每 2–5 秒刷新，显示进度和实时指标
2. 点击取消后 5 秒内停止发送新请求
3. 可以对失败 Run 执行人工重试
4. 可以从历史任务一键复测，展示配置差异
5. 取消和重试操作幂等

**需求映射：**
- MON-01: 查看任务和 Run 状态
- MON-02: 查看当前并发和 RPS
- MON-03: 查看实时性能指标
- MON-04: 页面自动刷新
- MON-05: 取消任务或 Run
- MON-06: 5 秒内停止新请求
- MON-07: 人工重试
- MON-08: 一键复测

**依赖：** Phase 5, Phase 6

**风险：**
- 取消操作需要正确处理在途请求
- 复测时配置差异检测需要全面

---

### Phase 8: 结果对比与可视化

**目标：** 实现跨 Run 结果对比、可比性检查和图表可视化。

**成功标准：**
1. 可以选择任意终态历史 Run 进行对比
2. 系统自动检查对比条件一致性
3. 条件一致标记"严格可比"，有差异标记"非严格可比"
4. 提供指标对比表、分位数图表、时间序列、错误分类图

**需求映射：**
- PROTO-01: 支持流式和非流式
- PROTO-03: 支持 Tool Calling
- PROTO-04: 保留完整原始响应
- PROTO-05: 未识别字段原样保留
- RESULT-04: 选择 Run 进行对比
- RESULT-05: 检查对比条件一致性
- RESULT-06: 标记可比性
- RESULT-07: 提供图表

**依赖：** Phase 7

**风险：**
- 图表库选择需要考虑离线报告兼容性

### Phase 9: 报告生成与导出

**目标：** 实现静态多页 HTML 报告生成、版本管理和数据导出。

**成功标准：**
1. 可以手工生成静态多页 HTML 报告
2. 完整请求内容在独立 `request-details.html` 中
3. 删除明细页后其他页面仍可查看
4. 报告可在断网 Chrome 中打开
5. 每次生成创建新版本
6. 可以添加人工备注
7. 可以导出 CSV 和 JSON

**需求映射：**
- RESULT-01: 查看任务汇总和明细
- RESULT-02: 查看完整 Prompt 和回答
- RESULT-03: 请求列表强制分页
- REPORT-01: 生成静态 HTML 报告
- REPORT-02: 独立明细页
- REPORT-03: 删除明细页后仍可查看
- REPORT-04: 断网可打开
- REPORT-05: 版本管理
- REPORT-06: 人工备注
- REPORT-07: 导出 CSV 和 JSON

**依赖：** Phase 8

**风险：**
- HTML 报告生成需要考虑大量数据时的性能
- 报告样式需要支持深色技术风格

### Phase 10: 安全加固与审计

**目标：** 实现密钥脱敏、内容转义、白名单校验、DNS rebinding 防护和审计日志。

**成功标准：**
1. 页面、日志、报告中 API Key 全部脱敏
2. 用户生成内容按纯文本转义，不执行脚本
3. CSV 导出公式字符安全转义
4. 域名/CIDR 白名单生效，阻止 SSRF
5. 防止 DNS rebinding
6. 关键操作写入审计日志

**需求映射：**
- SUPP-08: 白名单阻止 SSRF
- REPORT-08: 导出数据脱敏
- SEC-01: 统一脱敏 API Key
- SEC-02: 纯文本转义
- SEC-03: CSV 公式转义
- SEC-04: 审计日志
- SEC-05: 重新解析域名并校验
- SEC-06: 防止 DNS rebinding
- SEC-07: 忽略 TLS 错误选项

**依赖：** Phase 9

**风险：**
- 脱敏规则需要覆盖所有输出路径
- DNS rebinding 防护需要每次连接时校验

**目标：** 实现仪表盘、组件健康检查、白名单配置和历史数据清理。

**成功标准：**
1. 仪表盘显示任务统计和异常摘要
2. 组件健康状态实时更新
3. 可以配置白名单并查看受影响连接
4. 可以预览并手工清理历史数据
5. 清理操作幂等，支持补偿重试

**需求映射：**
- SYS-01: 仪表盘
- SYS-02: 组件健康状态
- SYS-03: 配置白名单
- SYS-04: 预览并清理历史数据
- SYS-05: 清理操作幂等
- SYS-06: 清理删除业务数据
- SYS-07: 清理保留配置数据

**依赖：** Phase 10

**风险：**
- 清理操作需要充分测试，避免误删
