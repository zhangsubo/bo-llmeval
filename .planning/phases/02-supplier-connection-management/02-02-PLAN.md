## 计划假设

- A-HTTP 客户端：使用 httpx.Client（同步），与 Phase 1 同步架构一致
- A-测试超时：连接超时 15s，读取超时 30s（PRD §9.5 默认值）
- A-流式解析：OpenAI SSE 格式（data: 行 JSON，data: [DONE] 终止）
- A-TTFT 计算：首个有效 chunk 到达时间 - 请求发送时间（冒烟级精度即可）
- A-同步策略：只新增不删除，已有记录（无论 source）不覆盖
- A-手工录入：POST /connections/{id}/models 创建 source=manual 的 model_deployment
- A-model ID 冲突：同步发现同 connection_id + model_id 已存在时跳过

       - `test_non_stream(base_url, api_key, model_id, timeout_connect=15, timeout_read=30) -> ConnectionTestResult`：
         a. 构造 Chat Completions 请求（messages=[{role:user, content:"Hello"}], max_tokens=5, stream=False）

         c. 计算 TTFT = 首个 "data: " 行（非 [DONE]）到达时间 - 请求开始时间
         d. 必须读到 "data: [DONE]" 才算完整
         e. 中间出现 error 字段记为 error
       - `run_connection_test(connection_id, model_id, db, crypto) -> dict`：
         a. 从 DB 读取连接信息
         b. 解密 api_key
         c. 依次调用 test_non_stream 和 test_stream

## Risks

| 风险 | 影响 | 缓解 |
|------|------|------|
| 供应商 API 格式不标准 | 模型同步失败 | 同步失败不阻断接入，记录错误供人工处理 |
| SSE 流式解析 edge case | 连接测试误判 | 测试必须读到 [DONE]，中间 error 记为失败 |
| httpx 流式请求在长响应时超时 | 测试中断 | 使用合理超时（read=30s），冒烟测试 max_tokens=5 响应很短 |
